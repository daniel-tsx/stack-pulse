## P1-R1: redirect dispatch bypass

**Root cause:** native fetch followed redirects internally. The shared authentication guard
ran only before application fetch calls, so a redirect could dispatch another HTTP request
after a peer had confirmed 401. The diagnostic's single fetch call could likewise issue
multiple HTTP requests.

**Change:** [the request loop](../../src/lib/github.ts) (line 80) uses `redirect: 'manual'`.
Repository GETs follow 301/302/303/307/308 explicitly, checking the existing shared auth
state immediately before every fetch, including follow-ups and retries. At most 20 follows
are allowed per attempt. Missing/malformed locations, credential-bearing URLs, different
origins and downgrade URLs produce a fixed `GITHUB_UPSTREAM` error without following or
retrying the rejected redirect. Only `https://api.github.com` targets are accepted.
The credential check rejects redirect responses and makes one HTTP request, without retry.

**Why explicit handling:** it controls the missing dispatch boundary directly. A shared
AbortController would introduce cancellation state and could interrupt otherwise successful
in-flight work. No controller is needed once native automatic redirects are disabled.
Started requests still settle; their successful inserts remain eligible for aggregation
and delivery. The original 8,000ms signal covers the whole redirect chain, including the
response body; the existing one network/5xx retry receives a fresh signal. A 401 sets shared
state synchronously before the error is propagated. Typed guard/redirect errors bypass the
network retry catch.

GitHub documents repository/API redirects as legitimate behavior, so rejecting every
repository redirect would regress healthy ingestion. The implementation follows safe API
targets while enforcing the guard. [GitHub redirect guidance](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api#follow-redirects).
Native fetch defaults to following redirects; this change makes that choice explicit.
[Fetch redirect modes](https://developer.mozilla.org/en-US/docs/Web/API/Request/redirect).

## P1-R2: lost committed processor progress

**Root cause:** iteration/filtering occurred outside the release catch. With
`[validRelease, null]`, the valid release committed, then filtering threw. The processor
rejected instead of returning its existing accumulated counters and inserted IDs. The
route's rejection fallback recorded zero inserts and scheduled no IDs from that processor.

**Change:** the GitHub helper rejects non-array payloads before processing. Each entry's
basic object/tag/draft/published-date shape and existing publishability check now execute
[inside the processor catch](../../src/lib/release-ingestion.ts) (line 94), with a `PROCESSING`
stage. Validation or unexpected filtering failures increment release failures and emit a
fixed, safe release-scoped error. Valid later entries continue. The function returns its
existing structured result, including earlier committed counts and IDs.

**Why safe:** insertion, lookup, summarization and the unique `(techId, version)` conflict
target are unchanged. Insert counts/IDs are still added only after a successful insert
returning an ID; attempted failed inserts contribute neither. No rollback, duplicate
retry or notification replay is added. The real cron's existing aggregation/finalizer now
receive the complete result. One committed release plus an invalid entry produces
`partial_success`, one processed/inserted release, one failed release and a durable
`completed_with_errors` row with matching counts. A later global DB failure still produces
`failed` while retaining earlier confirmed inserts. All-invalid entries produce `failed`.

The fix closes the reproduced rejection path at its source; it does not guess committed
counts from a rejected promise. The existing `releaseCountersComplete:false` fallback
remains for errors outside the result boundary. Unknown DB acknowledgement outcomes and
audit finalization failures still require operational reconciliation.

## Regression evidence

The new tests execute the actual handlers, fetcher, processor and finalizer. HTTP tests use
native Node fetch with a small network-free dispatcher implementing the documented
dispatcher interface. Its dispatch hook observes internal HTTP requests, including native
redirect follows; it does not replace fetch with a canned-response function. No real socket,
GitHub endpoint or production client is used. [Node custom dispatcher API](https://nodejs.org/api/globals.html#custom-dispatcher).
The shared context setter releases delayed responses only after the real 401 assignment,
so the overlap cases do not depend on timer ordering.

Before the fixes, 11 of the 18 focused tests failed. The two core reproductions included
HTTP 200 from the redirecting health check, seven dispatches instead of six after 401,
and HTTP 500/lost progress after a committed insert. After the fixes, all 18 pass:

- Health redirect: one native GET dispatch, failed diagnostic, no DB/AI/delivery work.
- Delayed redirect, 5xx and network failure after peer 401: six dispatches, zero after
  confirmation, six later repositories deferred, four settled inserts/IDs retained in
  response and durable mock run state.
- Healthy absolute 301 and relative 307 redirects: successful ingestion and delivery IDs.
- Invalid/external/downgrade/credential-bearing redirects and loops: safe bounded rejection.
- Redirected 5xx: one retry, shared timeout within each chain and fresh timeout on retry.
- Timeout: production requests still ask for 8,000ms; accelerated signals abort actual
  native fetch, which retries once. The test uses 5ms signals instead of waiting 16 seconds.
- Committed insert followed by a validation throw; invalid entry before insert; all invalid;
  all successful; non-array payload; release-specific/global DB insert failure after a
  commit. Assertions cover persisted mock rows, run status/details/counters and exact IDs.
- Repeated invocations: existing rows deduplicate, first audit row is preserved, and no
  committed ID is scheduled twice. Custom ingestion keeps optional auth/legacy finalization.

The DB fixture now models `running`/zero defaults and updates the requested run ID, rather
than silently updating the most recent row. Existing tests additionally assert equal-length
wrong-secret denial, empty headers, blank tokens and the diagnostic's Bearer credential.
The original 34 tests still pass, covering 403/429/5xx classification, cron outcomes,
filters/prereleases, AI behavior, no-ops, auth, global failures and retained writes.
