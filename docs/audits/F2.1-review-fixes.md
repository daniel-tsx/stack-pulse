## 3. Execution deadline design

The clock starts at the first statement of the authorized route's execution path
([route](<C:/Work/Side Projects/stack-pulse/src/app/api/cron/fetch-releases/route.ts:30>)).
Authentication still precedes any DB, GitHub or AI work. All cutoffs use the same
`performance.now()` origin; cleanup allowances do not reset the invocation clock.

| Absolute elapsed time | Admission/cancellation behavior                                                                                                                                               |
| --------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Before 270s           | Selection, GitHub discovery, release filtering, lookups, AI and inserts share one work signal. New chunks/releases, lookup/AI/insert admission require at least 1s remaining. |
| At 270s               | Abort supported in-flight ingestion requests and retry sleeps. Queued work settles without dispatch. Await started processors before finalization.                            |
| Until 285s            | Attempt finalization using a separate DB signal. The 15s reserve is available when processing reaches its cutoff; earlier completion can finalize immediately.                |
| Until 295s            | Optional webhook preparation/delivery uses a separate cleanup signal. It runs after the finalization attempt and does not extend the clock.                                   |
| 295–300s              | Intended response/logging margin before Vercel's hard limit.                                                                                                                  |

GitHub keeps its 8s request cap and one network/5xx retry, further constrained by remaining
work time. AI keeps its 25s request cap, three application attempts, default concurrency
one and optional maximum two. Native body reading receives the combined signal.
Neon inherits `fetchOptions.signal` through the installed Drizzle HTTP adapter
([scoped DB](<C:/Work/Side Projects/stack-pulse/src/db/index.ts:10>)); the adapter regression
executes the actual libraries with a replaced transport and verifies cancellation reaches fetch.

Cleanup may legitimately start after the processing cutoff, within its own reserve.
Finalization never uses the already-aborted work signal. No `Promise.race` substitutes
for cancelling an outstanding operation. Both parallel selection reads use
`Promise.allSettled`; every started repository processor is awaited. All budget timers
and the progress interval are cleared in route `finally`.

## 4. Cancellation, counters and observability

The release result boundary keeps earlier acknowledged counters and returned IDs even
after later processing or persistence fails
([processor](<C:/Work/Side Projects/stack-pulse/src/lib/release-ingestion.ts:64>)).
An acknowledged insert at the cutoff remains successful. A cancelled or globally failed
write without an acknowledged result has an uncertain remote outcome: no success count
or guessed notification ID is added, and `releaseCountersComplete:false` is returned.
Confirmed database SQLSTATE failures retain their database scope, even if the cutoff
fires concurrently. A confirmed GitHub 401 remains global and blocks further GitHub dispatches.

For settled processor results:

- `discovered = processed + failed + skipped + deferred`.
- `processed` includes existing tags and conflict no-ops; `inserted` is a subset.
- `skipped` counts filtered entries; `deferred` counts returned entries never started,
  which can include drafts because they have not been filtered yet.
- `cancelled` is a subset of failed release operations, not another additive category.
- A cancelled discovery reports a repository error and zero invented release counts.
- Rejected processors and uncertain writes flag incomplete confirmed counts.

AI logical failures, attempts, retries and cooldowns remain separate. Queued deadline
rejections can fail with zero HTTP attempts. Successful AI followed by a failed insert
does not become successful ingestion. Deadline errors retain safe AI details where
available. Finalization failures return failed/HTTP 500 and `runFinalized:false` while
preserving confirmed response counters. Stored run rows still contain only the existing
aggregate fields and details, not the new completeness/timing metadata.

The attempt signal takes precedence over a 429/5xx retained by an aborted SDK body read
([scheduler](<C:/Work/Side Projects/stack-pulse/src/lib/ai-resilience.ts:272>)).
Such cancellation is terminal, retains the HTTP status and creates no cooldown or retry.
Global cancellation also aborts cooldown sleep; waiting lanes release through `finally`.

Lightweight metrics aggregate `repositorySelection`, `githubDiscovery`, `databaseLookup`,
`databaseWrite`, `aiQueue`, `aiRequest`, `aiRetryWait`, `finalization`,
`notificationPreparation` and `notificationDelivery`. Each records operation count,
active count and elapsed duration using a monotonic clock. Progress logs every 30s include
run ID, elapsed/remaining work time, metrics and confirmed chunk counters. Completion
logs/responses include elapsed time and metrics. There is no new per-release timing log.

Durations sum operation time: concurrent stages overlap and cannot be summed into
invocation wall time. Active durations accrue when operations settle; progress active
counts still identify pending stages if completion never runs. Chunk counters update
after chunk settlement. Logs exclude raw payloads, credentials, provider headers,
prompts and webhook URLs. Existing safe AI logs retain repository/release IDs.

## 5. HTTP 200 provider-error handling

Before inspecting summary content, the selected completion checks top-level `error`,
`choices[0].error`, and `choices[0].finish_reason === 'error'`
([guard](<C:/Work/Side Projects/stack-pulse/src/lib/ai.ts:240>)).
Known envelopes require an object with an integer error code in the HTTP-error range.
Their headers, HTTP status and envelope feed the existing internal classifier; only
sanitized metadata is emitted. HTTP 200 stays visible alongside numeric upstream code.

Rate limits/overload/unavailability use the existing bounded retry policy. Authentication
and credits remain nonretryable and block futile queued work. Missing/malformed error
details become a nonretryable invalid response. Partial content accompanying a provider
error is never accepted or inserted. Valid summary JSON still passes the same Zod schema;
an ordinary extra `error` field inside that content is not interpreted as a transport envelope.

## 7. Known limitations

- Cancellation is cooperative. Hard termination, cold-start/import time before route
  entry, blocked event loops or a transport ignoring abort can still prevent cleanup.
  Remote SQL/provider computation may continue after HTTP cancellation.
- There is no checkpoint of counters during processing. A hard kill or failed audit
  update can still leave `running`/zero counters despite committed release rows.
- Concurrency one is a rate-limit guard, not a throughput guarantee. Six repositories
  with five unseen releases require up to 30 serial AI operations. At 25s per operation
  that alone is 750s; multiple retries can be longer. F2.1 bounds/defer work, rather than
  guaranteeing every normal or recovered backlog fits 270s.
- Selection order and latest-five discovery are unchanged. Later chunks/older release
  gaps can remain undiscovered. No durable resume cursor or F3 backfill was introduced.
- Notification delivery has no durable outbox/receipt ledger. Ingestion status is stored
  before delivery; delivery errors/deadline flags appear in response/logs separately.
- Custom ingestion and standalone summaries retain their optional F2 contexts; the new
  whole-invocation reserves apply to the scheduled cron, not every caller.

## 8. October 10 timeout recovery

User-supplied production evidence: HTTP 504/`FUNCTION_INVOCATION_TIMEOUT` at 300s; a run
remained `running` with zero durable counters, while 44 release rows were created during
the invocation window. No production request or DB inspection was performed in F2.1.
This is consistent with inserts committing before the final aggregate audit update.
It does not identify which awaited stage consumed the time or prove every window-matched
row belongs exclusively to that invocation.

F2.1 preserves confirmed inserts, attempts finalization inside the reserve and reports
unknown commit outcomes. Later cron runs retain the unique `(tech_id, version)` constraint,
lookup and conflict no-op path, preventing duplicate release rows. Only IDs returned by
successful inserts are notified. This also means existing committed rows whose original
notification was interrupted are not automatically notified again.

Future stale-run maintenance must be explicitly authorized and reviewed separately:

1. Confirm the invocation has ended and establish a conservative stale threshold. Correlate
   run ID/timestamps with invocation logs; allow for clock skew, overlapping cron runs and
   custom ingestion. A time-window count is candidate evidence, not exact attribution.
2. Preserve every release row and its unique key. Reconstruct only provable counts; record
   unknown counters/details explicitly instead of equating zero audit counts to zero inserts.
3. Prepare a narrowly scoped, idempotent update for the identified stale run, using the
   existing `failed` status and an explicit incomplete-recovery note where appropriate.
   Review the dry-run evidence and predicate before any production mutation. Do not mark
   it completed solely because candidate rows exist.
4. Reconcile notification outcomes independently. A request may have been accepted before
   termination without a local acknowledgement. Do not replay unknown sends automatically;
   any approved replay needs its own duplicate-delivery policy.

No stale row is inspected, rewritten or repaired automatically by this patch.
